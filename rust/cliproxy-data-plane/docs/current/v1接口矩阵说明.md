# CPA v1接口矩阵说明

本文档整理仓库当前已实现的 `v1` 打头接口，并按运行时归属拆分为两部分：

- Go 主服务提供的 CPA 原生接口
- `rust/cliproxy-data-plane` 提供的 Rust 数据平面接口

仓库代码是事实来源。如果实现发生变化，应同步更新本文档和相关运行时文档。

## 1. CPA 原生 v1 接口

这些路由由 Go 主服务在 `internal/api/server.go` 中注册。

| 接口 | 请求协议 | 上游 provider | 是否支持流式 | 备注 |
| --- | --- | --- | --- | --- |
| `GET /v1/models` | 统一模型列表接口 | `openai` 或 `claude`，按请求形态分流 | 否 | 默认返回 OpenAI 风格模型列表；带 `Anthropic-Version` 时返回 Claude 风格；带 `client_version` 查询参数时返回 Codex client catalog 格式。 |
| `POST /v1/chat/completions` | OpenAI Chat Completions | 按模型路由到兼容执行链，常见包括 `openai`、`codex`、`xai` 或其他 OpenAI-compatible provider | 是 | 支持普通响应和流式响应。若客户端误把 Responses 格式发到该接口，服务端会先做规范化。 |
| `POST /v1/completions` | OpenAI Completions | 先转换成 Chat Completions，再走同一套兼容执行链 | 是 | 兼容 OpenAI 旧版 completions 协议。 |
| `POST /v1/images/generations` | OpenAI Images API 风格 | 按模型路由到 `codex`、`xai`、`openai-compat` 或基于 Responses 的图像工具链 | 是 | 支持 JSON 请求，并会按模型做请求改写。 |
| `POST /v1/images/edits` | OpenAI Images Edits 风格 | 按模型路由到 `codex`、`xai`、`openai-compat` 或基于 Responses 的图像工具链 | `待确认` | 同时支持 JSON 和 `multipart/form-data`。完整流式覆盖范围需要结合实现和测试进一步确认。 |
| `POST /v1/videos` | xAI 原生视频协议别名 | `xai` | 否 | 这是 xAI 原生 generations 风格入口的别名，不是 `/openai/v1/videos` 那套 OpenAI 风格视频接口。 |
| `POST /v1/videos/generations` | xAI 原生视频协议 | `xai` | 否 | xAI 原生视频生成接口。 |
| `POST /v1/videos/edits` | xAI 原生视频协议 | `xai` | 否 | xAI 原生视频编辑接口。 |
| `POST /v1/videos/extensions` | xAI 原生视频协议 | `xai` | 否 | xAI 原生视频扩展接口。 |
| `GET /v1/videos/:request_id` | xAI 原生视频查询协议 | `xai` | 否 | 按 `request_id` 查询 xAI 视频任务状态或结果。 |
| `POST /v1/messages` | Anthropic Claude Messages | 主要是 `claude`；精确下游执行器仍取决于模型路由 | 是 | 支持 Claude 兼容的非流式和流式请求。 |
| `POST /v1/messages/count_tokens` | Anthropic Count Tokens | `claude` count path | 否 | Claude 兼容 token 计数接口。 |
| `GET /v1/responses` | OpenAI Responses WebSocket | 主要是 `codex` 和 `xai`，按模型与 auth 能力选择 | 是，WebSocket | 双向实时 Responses 会话入口。 |
| `POST /v1/responses` | OpenAI Responses HTTP | 配置了 Rust data plane 时走 Rust；否则走 Go 原生 Responses 执行链 | 是 | 当 `data-plane.responses-base-url` 或对应 runtime 配置生效时，Go 会把该接口反向代理到 Rust。 |
| `POST /v1/responses/compact` | OpenAI Responses Compact | 路由到支持 compact 的后端，常见是 `codex`、`xai` 或其他兼容执行器 | 否 | 明确拒绝 `stream=true`。 |
| `GET /v1beta/models` | Gemini Models | `gemini` | 否 | Gemini 兼容模型列表接口。 |
| `POST /v1beta/models/*action` | Gemini API action 路由 | `gemini` | 是，取决于具体 action | 用于 Gemini 的动作接口，例如 `:generateContent`。 |
| `GET /v1beta/models/*action` | Gemini 单模型详情接口 | `gemini` | 否 | 返回单个 Gemini 模型描述。 |

## 2. Rust 数据平面 v1 接口

这些路由由 `rust/cliproxy-data-plane` 提供。当前实现范围刻意保持很窄。

| 接口 | 请求协议 | 上游 provider | 是否支持流式 | 备注 |
| --- | --- | --- | --- | --- |
| `POST /v1/responses` | OpenAI Responses HTTP | 当前真实热路径主要是 `codex`；更广泛 provider 覆盖范围按当前实现状态仍属 `待确认` | 是 | 这是 Rust 数据平面当前唯一真实承接的 `v1` 业务接口。它基于 runtime snapshot 完成模型解析、auth 选择、重试候选生成和上游执行。 |

## 3. 与本文相关但不属于 v1 打头的别名接口

下面这些接口在读代码时经常会一起出现，但它们本身不属于“`/v1` 打头接口”：

- `/backend-api/codex/responses`
- `/backend-api/codex/responses/compact`
- `/openai/v1/videos`
- `/openai/v1/videos/:video_id`
- `/openai/v1/videos/:video_id/content`

## 4. 代码定位

- Go 路由注册：`internal/api/server.go`
- Go OpenAI 兼容 handlers：`sdk/api/handlers/openai/`
- Go Claude 兼容 handlers：`sdk/api/handlers/claude/`
- Go Gemini 兼容 handlers：`sdk/api/handlers/gemini/`
- Rust HTTP 路由注册：`rust/cliproxy-data-plane/src/http.rs`
- Rust 当前实现架构说明：`rust/cliproxy-data-plane/docs/current/当前架构说明.md`

## 5. `POST /v1/responses`：CPA 已有能力 vs RS 当前能力

本节只比较 **HTTP `POST /v1/responses` 主链路**。

不包含：

- `GET /v1/responses` WebSocket
- `POST /v1/responses/compact`
- Codex `/backend-api/codex/responses*` 别名入口

| 能力项 | CPA `POST /v1/responses` | RS 当前 `POST /v1/responses` | 差异结论 | 备注 |
| --- | --- | --- | --- | --- |
| 基本 HTTP JSON ingress | 已支持 | 已支持 | 基本对齐 | 两边都能接收标准 JSON 请求并进入各自执行链。 |
| 非流式返回 | 已支持 | 已支持 | 基本对齐 | CPA 直接走 Go responses handler；RS 直接返回上游 JSON，或在特定 Codex 场景下把上游流聚合为 JSON。 |
| 流式 SSE 返回 | 已支持 | 已支持 | 基本对齐，但实现深度不同 | 两边都能向下游返回 SSE。CPA 有更完整的 SSE 分帧与修复逻辑；RS 当前主打直接透传上游流。 |
| 非法 JSON 请求处理 | 已支持 | 已支持 | 基本对齐 | CPA 通过 `ReadRequestBody` 和 handler 校验返回 `400`；RS 通过 Axum `JsonRejection` 返回 `400 invalid_json`。 |
| 压缩请求体解码 | 已支持 | 未见等价支持 | RS 落后 | CPA `ReadRequestBody` 支持 `Content-Encoding: zstd`；RS 当前直接使用 Axum `Json` extractor，仓库内未见等价压缩解码实现。 |
| provider 覆盖范围 | 更广 | 当前偏窄 | RS 落后 | CPA 面向 OpenAI Responses 兼容执行链；RS 当前文档明确说明 `/v1/responses` 主链路主要按 Codex 场景设计和验证。 |
| 路由选型成熟度 | 更高 | 当前偏 Codex-only | RS 落后 | RS 当前 `RouterCore` 在 `/v1/responses` 路径里实际固定选择 `ProviderKind::Codex`，尚不能视为对 CPA 路由语义的一比一复刻。 |
| 请求协议面宽度 | 更宽 | 当前偏窄 | RS 落后 | RS 当前 `ResponsesRequest` 仅显式覆盖 `model / stream / input / instructions / metadata / store` 等核心字段，仍不能证明已完整覆盖 CPA 的请求字段面。 |
| Codex 特化请求归一化 | 已有相关兼容逻辑 | 已支持一部分 | 部分对齐 | RS 会对 Codex 请求做 `store=false`、清空 `metadata`、补默认 `instructions`、字符串 `input` 改写等处理，但仍是 Codex 场景优先，不代表整体行为完全等价。 |
| 上游账号级切换 / 重试 | 已有多账号路由能力 | 已支持最小闭环 | 部分对齐 | RS 已实现按 `retry_candidates` 的 auth retry chain，可覆盖 `401/403/429 usage_limit_reached` 等典型 Codex 错误；是否完全覆盖 CPA 的所有切换语义仍需进一步逐项对比，当前记为 `待确认`。 |
| 流式 SSE 分帧修复 | 已支持 | 已支持最小闭环 | 部分对齐 | CPA 会修复分片 SSE、补 `response.completed.output`、处理多行 `data:` 等；RS 当前已补上 HTTP `POST /v1/responses` 主链路所需的最小 framer，支持 split frame 重组、`response.completed.output` 补齐和流尾 flush，但覆盖范围仍小于 CPA 全量 Responses 兼容层。 |
| 上游不可用时的兜底策略 | 直接报错 | 仍保留 mock fallback | 行为不同 | RS 当前在真实 upstream 不可用时仍可走 mock `streaming_response` / `non_streaming_response` 分支，这和 CPA 生产语义不等价。 |
| 对 CPA 行为的一比一复刻程度 | 否 | 否 | 尚未完成 | 当前更准确的描述是：RS 已实现可运行主链路，但仍是以 Codex 场景为中心的 MVP，而不是 CPA `POST /v1/responses` 的完整等价实现。 |
