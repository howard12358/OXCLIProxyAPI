# CLIProxyAPI Rust 数据平面契约测试手册

## 0. 目标

本文档用于给 `OXCLIProxyAPI/tree/rusty` 补齐 6 类关键契约测试：

1. Go 原生 `/v1/responses` vs Rust `/v1/responses` golden test；
2. SSE event golden test；
3. auth 401/403/429 切换测试；
4. stream 中途断开测试；
5. usage queue RESP + HTTP fallback 双路径测试；
6. snapshot exporter Go 结构和 Rust `common-types` schema 对齐测试。

这些测试的目标不是单纯追求覆盖率，而是把 **Go 控制面 / Rust 数据面 / 上游协议 / 客户端兼容性** 之间的边界钉死。

当前 Rust 数据平面的定位是专门承接 `/v1/responses`，从 Go 拉取 runtime snapshot，本地维护只读快照，做模型解析、账号选择、会话粘性、重试候选生成，并请求 OpenAI/Codex Responses 上游。这个边界已经在当前架构说明里明确。

# 2. 通用测试原则

## 2.1 golden test 不比较所有字段

Responses 协议里有很多运行时字段不稳定，例如：

```text
id
created_at
usage
latency_ms
ttft_ms
request_id
response_id
timestamp
```

golden test 需要先做 normalize，再比较。

建议定义统一 normalizer：

```text
normalize_response_json()
normalize_sse_frames()
normalize_usage_payload()
normalize_snapshot()
```

常见规则：

```text
1. 删除动态 ID；
2. 删除时间戳；
3. 删除 request_id / upstream request id；
4. 对 object key 排序；
5. SSE frame 按 event + data 归一；
6. JSON 字段中 null / 缺省字段按项目约定统一；
7. usage 中 latency、ttft 只校验存在性和类型，不校验具体值；
8. headers 只校验关键字段，不比较全部 headers。
```

## 2.2 分三层测试

建议分成三层：

```text
单元契约测试：
  不启动真实 HTTP 服务，直接测 protocol/sse/failure/router 等模块。

进程内集成测试：
  启动 Rust axum server + mock upstream，使用 fixture snapshot。

跨语言契约测试：
  Go exporter 输出 snapshot，Rust common-types 反序列化校验；
  Go 原路径和 Rust 路径输出做 golden diff。
```

## 2.3 不依赖真实 Codex / OpenAI

这些契约测试不要请求真实上游。
全部用 mock upstream，例如：

```text
wiremock-rs
httpmock
axum test server
Go httptest.Server
```

这样测试才能稳定、快速、可重复。

# 3. 契约测试一：Go 原生 `/v1/responses` vs Rust `/v1/responses` golden test

## 3.1 测试目的

验证同一个下游请求，在 Go 原生路径和 Rust 数据面路径下，输出语义一致。

这里不是要求字节完全一致，而是要求：

```text
1. HTTP status 一致；
2. 关键 headers 一致；
3. 非流式 JSON 结构一致；
4. stream=false 聚合结果一致；
5. error body 结构一致；
6. OpenAI Responses 客户端可消费行为一致。
```

当前 Rust 热路径只覆盖 `/v1/responses`，并且路径中会检查 route、读取 snapshot、生成 execution plan、执行 upstream、返回 JSON/SSE。

## 3.2 测试输入

准备几类请求：

```text
responses_basic.json
responses_with_instructions.json
responses_with_tools.json
responses_with_reasoning.json
responses_stream_false_but_upstream_sse.json
responses_invalid_model.json
responses_route_disabled.json
```

示例：

```json
{
  "model": "gpt-5-codex",
  "input": "hello",
  "stream": false
}
```

## 3.3 测试流程

```text
1. 启动 mock upstream；
2. mock upstream 根据请求返回固定 JSON 或固定 SSE；
3. 启动 Go 原生服务；
4. 启动 Rust data-plane 服务；
5. 两边使用同一份配置语义：
   - 同一模型别名；
   - 同一 auth；
   - 同一 upstream base_url；
   - 同一 route enabled 状态；
6. 对同一个 request 分别请求：
   - Go:   POST /v1/responses
   - Rust: POST /v1/responses
7. 对响应做 normalize；
8. 和 golden 文件比较；
9. Go 与 Rust 的 normalized output 互相比较。
```

当前已落地的最小闭环使用同一份 fixture：

```text
testdata/contract/responses/non_stream_aggregates_codex_stream.json
```

Go 侧测试入口：

```bash
go test ./sdk/api/handlers/openai -run TestOpenAIResponsesNativeCodexMatchesSharedGoldenFixture -count=1
```

Rust 侧测试入口：

```bash
cargo test --manifest-path rust/cliproxy-data-plane/Cargo.toml --test contract responses_golden
```

## 3.4 断言内容

非流式成功响应：

```text
assert status == 200
assert content-type contains application/json
assert normalized_json == golden_json
assert normalized_go_json == normalized_rust_json
```

错误响应：

```text
assert status 一致
assert error.type 一致
assert error.code 一致
assert error.message 允许模糊匹配，不能完全自由漂移
```

例如：

```json
{
  "error": {
    "message": "...",
    "type": "invalid_request_error",
    "code": "routing_unavailable"
  }
}
```

## 3.5 Rust 测试骨架

```rust
#[tokio::test]
async fn responses_basic_matches_golden() {
    let upstream = start_mock_upstream("fixtures/upstream/codex_response_non_stream.json").await;
    let snapshot = load_snapshot_with_upstream("fixtures/snapshots/codex_one_account.json", upstream.url());

    let app = start_data_plane_with_snapshot(snapshot).await;

    let request = load_json("fixtures/requests/responses_basic.json");
    let response = app.post("/v1/responses").json(&request).send().await;

    assert_eq!(response.status(), 200);

    let actual = response.json::<serde_json::Value>().await;
    let actual = normalize_response_json(actual);

    let expected = load_json("fixtures/golden/responses_basic.normalized.json");
    assert_json_eq!(actual, expected);
}
```

## 3.6 Go + Rust 对比测试骨架

```text
TestResponsesGolden_GoVsRust
  - startMockUpstream()
  - startGoServer()
  - startRustDataPlane()
  - post same request
  - normalize both
  - cmp.Diff(goNormalized, rustNormalized)
```

## 3.7 通过标准

这类测试通过后，只能说明：

```text
Rust 当前实现和 Go 当前行为一致。
```

不能说明：

```text
Rust 完整兼容 OpenAI Responses 协议。
```

所以这个测试要和 SSE golden test、真实客户端 smoke test 配合使用。

# 4. 契约测试二：SSE event golden test

## 4.1 测试目的

验证 Rust 对 SSE 的处理不会破坏 OpenAI Responses stream 格式。

当前 Rust 已经实现了最小 SSE framer，用来重组被拆开的 `event:` / `data:` chunk，并在 `response.completed.response.output` 为空时，用之前记录的 `response.output_item.done` 补齐 output。

因此 SSE 测试要重点覆盖：

```text
1. 正常 SSE 原样透传；
2. event/data 被拆 chunk 后重组；
3. 尾部没有完整分隔符时 flush；
4. completed.output 为空时 repair；
5. 多个 output_item.done 时顺序保持；
6. data: [DONE] 是否正确保留或处理；
7. 非 JSON data 不导致 panic；
8. 上游错误帧不被吞掉。
```

## 4.2 fixture 示例

`fixtures/upstream/sse_basic.txt`

```text
event: response.created
data: {"type":"response.created","response":{"id":"resp_1"}}

event: response.output_item.done
data: {"type":"response.output_item.done","item":{"id":"item_1","type":"message","content":[{"type":"output_text","text":"hello"}]}}

event: response.completed
data: {"type":"response.completed","response":{"id":"resp_1","output":[{"id":"item_1","type":"message","content":[{"type":"output_text","text":"hello"}]}]}}

data: [DONE]
```

`fixtures/upstream/sse_completed_missing_output.txt`

```text
event: response.output_item.done
data: {"type":"response.output_item.done","item":{"id":"item_1","type":"message","content":[{"type":"output_text","text":"hello"}]}}

event: response.completed
data: {"type":"response.completed","response":{"id":"resp_1","output":[]}}

data: [DONE]
```

## 4.3 normalize 规则

SSE normalize 建议拆成结构化 frame：

```rust
struct NormalizedSseFrame {
    event: Option<String>,
    data: String,
}
```

规则：

```text
1. \r\n 统一为 \n；
2. 多个 data: 行合并；
3. 空行作为 frame 分隔；
4. JSON data 做 JSON normalize；
5. [DONE] 保持字符串；
6. event 缺省则为 None，不强行补 event。
```

## 4.4 单元测试骨架

```rust
#[test]
fn sse_reassembles_chunked_frames() {
    let chunks = vec![
        b"event: response.output".to_vec(),
        b"_item.done\ndata: {\"type\":\"response.output_item.done\"".to_vec(),
        b",\"item\":{\"id\":\"item_1\"}}\n\n".to_vec(),
    ];

    let actual = run_sse_framer(chunks);
    let normalized = normalize_sse(&actual);

    let expected = load_sse_golden("fixtures/golden/sse_chunked.normalized.txt");
    assert_eq!(normalized, expected);
}
```

## 4.5 completed repair 测试

```rust
#[test]
fn sse_repairs_completed_output_from_output_item_done() {
    let input = load_bytes("fixtures/upstream/sse_completed_missing_output.txt");

    let actual = run_sse_repair(input);
    let frames = normalize_sse(&actual);

    let completed = find_event(&frames, "response.completed");
    let data = parse_json(completed.data);

    assert_eq!(
        data["response"]["output"][0]["id"],
        "item_1"
    );
}
```

## 4.6 集成测试

```text
1. mock upstream 返回 chunked SSE；
2. Rust /v1/responses stream=true 请求；
3. 客户端逐 chunk 读取；
4. normalize 后和 golden 比较；
5. 确认 content-type 是 text/event-stream；
6. 确认没有丢 event；
7. 确认 completed repair 生效。
```

## 4.7 通过标准

```text
1. SSE frame 边界稳定；
2. event 顺序不变；
3. JSON data 语义不变；
4. completed repair 只在 output 为空时发生；
5. 不会因为上游 chunk 切分方式不同导致输出不同。
```

# 5. 契约测试三：auth 401/403/429 切换测试

## 5.1 测试目的

验证 Rust 数据面遇到账号级失败时，只在允许的阶段和允许的错误类型上切换账号。

当前 Rust `/v1/responses` 已经具备账号级重试链，典型触发切换的错误包括 Codex 401、403、429 usage_limit_reached、account_deactivated、invalid_api_key。

## 5.2 核心语义

必须钉死以下规则：

```text
1. pre-commit 失败可以切换账号；
2. post-commit 失败不能切换账号；
3. 401/403 视为 auth-bound failure；
4. 429 usage_limit_reached 视为 auth quota failure；
5. 普通 429 rate_limit 是否切换必须明确；
6. 账号进入 cooldown 后，后续请求不能继续选中它；
7. auth+model cooldown 和 auth cooldown 要区分；
8. 所有账号失败后返回明确错误。
```

这里的 pre-commit 指：

```text
还没有向下游客户端写出响应头 / 首个 SSE frame。
```

post-commit 指：

```text
已经向下游客户端写出 200 / text/event-stream，或者已经发送过至少一个 SSE frame。
```

## 5.3 fixture snapshot

`codex_two_accounts.json`：

```json
{
  "auth_pool": [
    {
      "id": "auth_bad",
      "provider": "codex",
      "enabled": true,
      "execution": {
        "codex": {
          "access_token": "bad-token",
          "base_url": "http://mock-upstream"
        }
      }
    },
    {
      "id": "auth_good",
      "provider": "codex",
      "enabled": true,
      "execution": {
        "codex": {
          "access_token": "good-token",
          "base_url": "http://mock-upstream"
        }
      }
    }
  ]
}
```

## 5.4 mock upstream 行为

根据 Authorization token 返回不同响应：

```text
bad-token:
  401 invalid_api_key

good-token:
  200 normal response
```

或：

```text
bad-token:
  429 usage_limit_reached

good-token:
  200 normal response
```

## 5.5 测试用例

### Case A：401 后切到第二个账号

```text
Given:
  auth_bad 排在第一
  auth_good 排在第二

When:
  POST /v1/responses

Then:
  第一次 upstream 请求使用 auth_bad
  返回 401
  Rust 标记 auth_bad 不健康
  第二次 upstream 请求使用 auth_good
  最终 client 收到 200
  usage payload 记录最终成功账号 auth_good
  errors channel 产生 auth_bad 的错误事件
```

### Case B：403 后切换

同 A，但错误是 403。

### Case C：429 usage_limit_reached 后切换

```json
{
  "error": {
    "code": "usage_limit_reached",
    "message": "You have reached your usage limit"
  }
}
```

断言：

```text
1. auth_bad 被 cooldown；
2. auth_good 被选中；
3. 最终成功；
4. 下一次请求不再选择 auth_bad。
```

### Case D：所有账号失败

```text
auth_1 -> 401
auth_2 -> 429 usage_limit_reached
auth_3 -> 403
```

断言：

```text
1. 尝试次数 == 候选账号数量；
2. 返回 502 或约定错误码；
3. error code 是 upstream_unavailable / auth_exhausted 之一；
4. errors channel 至少有对应失败事件；
5. 不 panic，不空响应。
```

### Case E：post-commit 后不切换

mock upstream：

```text
1. 先返回 200 text/event-stream；
2. 发送一个 response.created frame；
3. 然后连接断开或发送错误。
```

断言：

```text
1. Rust 不再请求 auth_good；
2. 客户端看到 stream 中断或错误 frame；
3. 不能把两个账号的 stream 混在一起。
```

## 5.6 Rust 测试骨架

```rust
#[tokio::test]
async fn retries_next_auth_on_401_before_commit() {
    let upstream = MockUpstream::new()
        .when_token("bad-token").return_401_invalid_api_key()
        .when_token("good-token").return_json_success();

    let snapshot = load_snapshot("fixtures/snapshots/codex_two_accounts.json")
        .with_upstream(upstream.url());

    let app = start_data_plane_with_snapshot(snapshot).await;

    let res = app
        .post("/v1/responses")
        .json(&load_json("fixtures/requests/responses_basic.json"))
        .send()
        .await;

    assert_eq!(res.status(), 200);

    upstream.assert_seen_token_order(vec!["bad-token", "good-token"]);
    assert_auth_unhealthy(&app, "auth_bad").await;
}
```

## 5.7 通过标准

```text
1. 401/403/usage_limit_reached 行为稳定；
2. retry 只发生在 pre-commit；
3. cooldown 生效；
4. retry candidate 顺序可预测；
5. 错误事件和 usage 事件不丢。
```

# 6. 契约测试四：stream 中途断开测试

## 6.1 测试目的

验证下游客户端断开连接时，Rust 是否正确取消上游请求，释放资源，不继续无限读取上游流。

这类测试非常关键，因为数据平面是 I/O 密集型网关。如果 stream abort 没处理好，会造成：

```text
1. 上游连接泄漏；
2. Rust task 泄漏；
3. usage 统计错误；
4. 账号额度被浪费；
5. Docker 内存持续上涨。
```

## 6.2 需要钉死的语义

建议明确成以下规则：

```text
1. 下游断开后，Rust 应尽快 drop response body；
2. 上游请求应被取消或连接应被关闭；
3. 不再向 usage queue 写入成功 completed；
4. 可以写入 canceled / client_aborted usage，前提是原统计链路支持；
5. post-commit 断流不触发 auth retry；
6. 日志中应有 client_aborted 或 stream_canceled 标记；
7. 不能 panic。
```

## 6.3 mock upstream 设计

mock upstream 需要支持慢速无限 SSE：

```text
event: response.created
data: {...}

每 100ms 发送一个 response.output_text.delta
永远不主动 completed
```

同时 mock upstream 记录：

```text
1. 连接是否被客户端关闭；
2. body future 是否被 drop；
3. 已发送 frame 数；
4. 是否收到 TCP reset / write error。
```

## 6.4 测试流程

```text
1. 启动 Rust data-plane；
2. mock upstream 返回无限 SSE；
3. client 请求 POST /v1/responses stream=true；
4. client 读取前 2 个 frame；
5. client 主动 drop response；
6. 等待 200ms ~ 1s；
7. 断言 mock upstream 观察到连接关闭；
8. 断言 Rust 没有继续读完整 stream；
9. 断言没有 auth retry；
10. 断言 usage queue 不产生 completed success。
```

## 6.5 Rust 测试骨架

```rust
#[tokio::test]
async fn downstream_abort_cancels_upstream_stream() {
    let upstream = MockStreamingUpstream::infinite_sse();
    let app = start_data_plane_with_upstream(upstream.url()).await;

    let mut res = app
        .post("/v1/responses")
        .json(&json!({
            "model": "gpt-5-codex",
            "input": "write slowly",
            "stream": true
        }))
        .send_streaming()
        .await;

    let _first = res.next_frame().await.unwrap();
    let _second = res.next_frame().await.unwrap();

    drop(res);

    tokio::time::sleep(Duration::from_millis(500)).await;

    assert!(upstream.connection_was_closed());
    assert_eq!(upstream.request_count(), 1);
    assert_no_retry_to_second_auth().await;
}
```

## 6.6 usage 断言

如果当前 usage queue 尚未定义 canceled 事件，先按保守规则：

```text
下游中途断开：
  不写 success usage；
  不写 completed usage；
  可以暂时只打 tracing log。
```

后续如果要支持 canceled usage，再新增 golden：

```json
{
  "status": "canceled",
  "finish_reason": "client_aborted",
  "stream": true
}
```

## 6.7 通过标准

```text
1. 下游断开后上游连接能释放；
2. 不发生 post-commit retry；
3. 不误记成功 usage；
4. 多次重复测试没有 task/connection 增长。
```

# 7. 契约测试五：usage queue RESP + HTTP fallback 双路径测试

## 7.1 测试目的

验证 Rust 产生的 usage payload 能被 Go 统计链路稳定消费。

当前 Rust 本地 usage queue 支持 FIFO pop、subscriber fan-out、`support_refresh` 首包、`refresh` 控制消息、HTTP `/v0/management/usage-queue?count=N`，以及 RESP 命令 `AUTH`、`SUBSCRIBE usage/errors`、`LPOP/RPOP usage`。架构文档也明确当前未完成 Home 模式 `LPUSH usage`、errors 通道真实生产来源、dashboard/alert runbook。

Go 侧已有 bridge：优先 RESP 订阅 Rust usage，再 fallback 到 HTTP pop。

## 7.2 需要测试的路径

```text
A. Rust usage queue HTTP pop
B. Rust usage queue RESP LPOP/RPOP
C. Rust usage queue RESP SUBSCRIBE usage
D. Go bridge RESP 正常消费
E. Go bridge RESP 失败后 HTTP fallback
F. subscriber 存在时 fan-out 行为
G. subscriber 不存在时 FIFO 入队行为
H. AUTH token 校验
```

## 7.3 usage payload 最小字段

建议 golden 只校验核心字段：

```json
{
  "timestamp": "...",
  "model": "gpt-5-codex",
  "provider": "codex",
  "auth_id": "auth_good",
  "stream": false,
  "status": "success",
  "http_status": 200,
  "latency_ms": 123,
  "ttft_ms": 50,
  "response_headers": {}
}
```

normalize：

```text
timestamp 删除或固定；
latency_ms 只校验 >= 0；
ttft_ms 只校验 stream 时存在；
headers 只保留 request-id 等关键项。
```

## 7.4 HTTP pop 测试

流程：

```text
1. 启动 Rust；
2. 发一个成功 /v1/responses 请求；
3. GET /v0/management/usage-queue?count=1；
4. 断言返回 1 条；
5. 再 GET 一次；
6. 断言队列为空。
```

骨架：

```rust
#[tokio::test]
async fn usage_queue_http_pop_is_fifo_and_consuming() {
    let app = start_data_plane().await;

    send_success_response_request(&app).await;
    send_success_response_request(&app).await;

    let first = app.get("/v0/management/usage-queue?count=1").send().await;
    let first_payload = parse_usage(first).await;

    let second = app.get("/v0/management/usage-queue?count=1").send().await;
    let second_payload = parse_usage(second).await;

    assert!(first_payload.timestamp <= second_payload.timestamp);

    let empty = app.get("/v0/management/usage-queue?count=1").send().await;
    assert_empty_queue(empty).await;
}
```

## 7.5 RESP LPOP/RPOP 测试

流程：

```text
1. 建 TCP 连接到 Rust listener；
2. AUTH token；
3. 发送 LPOP usage；
4. 解析 RESP bulk string；
5. JSON parse；
6. 和 normalized usage golden 比较。
```

RESP 示例：

```text
*2\r\n$4\r\nAUTH\r\n$12\r\nsecret-token\r\n
*2\r\n$4\r\nLPOP\r\n$5\r\nusage\r\n
```

断言：

```text
1. AUTH 成功；
2. LPOP 返回 bulk string；
3. payload 是合法 JSON；
4. 第二次 LPOP 为空；
5. 错误 token 被拒绝。
```

## 7.6 RESP SUBSCRIBE 测试

流程：

```text
1. TCP 连接；
2. AUTH；
3. SUBSCRIBE usage；
4. 断言收到 subscribe ack；
5. 发一个 /v1/responses 成功请求；
6. 断言 subscriber 收到 usage message；
7. 再 HTTP pop；
8. 如果当前语义是有 subscriber 时不入内存队列，则 HTTP pop 应为空。
```

这个规则很重要，因为当前 usage queue 语义是：有订阅者时直接广播，不再写入内存队列；没有订阅者时进入 FIFO。

## 7.7 Go bridge fallback 测试

Go 侧建议写 `dataplane_usage_bridge_contract_test.go`。

Case A：RESP 正常

```text
1. fake Rust RESP server；
2. Go bridge 连接 SUBSCRIBE usage；
3. fake server 推送 usage payload；
4. 断言 Go redisqueue.Enqueue 被调用。
```

Case B：RESP 失败，HTTP fallback

```text
1. RESP server 拒绝连接或断开；
2. fake HTTP server 提供 /v0/management/usage-queue；
3. Go bridge fallback 到 HTTP；
4. 断言 payload 被 enqueue。
```

## 7.8 通过标准

```text
1. HTTP pop 消费语义稳定；
2. RESP LPOP/RPOP 消费语义稳定；
3. RESP SUBSCRIBE fan-out 语义稳定；
4. AUTH 行为稳定；
5. Go bridge fallback 可用；
6. usage payload 字段不漂移。
```

# 8. 契约测试六：snapshot exporter Go 结构和 Rust common-types schema 对齐测试

## 8.1 测试目的

验证 Go 导出的 runtime snapshot 永远能被 Rust `common-types` 反序列化，并通过 Rust 的最小校验。

当前 Rust 与 Go 的核心边界是 `RuntimeSnapshot`，Rust 依赖字段包括 version、generated_at、source_instance_id、listeners.public_http、routes.responses、routing、providers、model_aliases、models、auth_pool、network.upstream_proxy 等。Rust 应用 snapshot 前会做最小校验，例如 version/generated_at/source_instance_id 不能为空，启用 provider 必须能在 models 找到，Codex OAuth auth 必须带 `execution.codex.access_token`。
